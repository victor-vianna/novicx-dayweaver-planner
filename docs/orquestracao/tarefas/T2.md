# T2 — Edge Function `admin-users`

- **Dono:** Claude · **Revisão:** CXR ★ (`xhigh`) · **Depende:** T1 · **Faixa:** `supabase/functions/admin-users/**`, `supabase/config.toml` (`[functions.admin-users]`), `vitest.config.ts`/`tsconfig.json` (include) · **Depois:** AH deploy no dev

## Objetivo

Único ponto com `service_role` (D1): a equipe cria acesso de cliente, bloqueia/desbloqueia,
gera link de definição de senha e troca e-mail, sem expor privilégio ao frontend.

## Abordagem

- `handler.ts`: lógica pura (sem Deno/Supabase), testada no vitest com dependências falsas.
  `index.ts`: entrada Deno que liga o handler a um cliente `service_role` (variáveis injetadas pelo Supabase).
- Toda ação exige JWT válido (`auth.getUser`) **e** admin ativo (`profiles.role = 'admin'`, `blocked_at is null`).
  `verify_jwt = false` no gateway porque o handler valida o chamador ele mesmo.
- `create_account`: cliente nova ou existente sem acesso → usuário Auth com e-mail confirmado → o trigger
  vincula; confere o vínculo, senão desfaz (usuário e, se criada agora, a cliente). Devolve `action_link` de recuperação.
- `set_access`: só contas `client`, nunca a própria; `blocked_at` primeiro (RLS nega na hora), depois ban no Auth.
- `reset_access`: link de recuperação (`generateLink`, sem e-mail); recusado para bloqueadas e admins.
- `update_email`: Auth e `clients.email` juntos; reverte o Auth se a cliente falhar.
- Erros de dependência viram mensagem genérica (sem detalhes internos); conflitos únicos → 409.

## Riscos

- `action_link` é equivalente a credencial: vai só para a admin autenticada, que o repassa. Não é logado.
- CORS `*`: autenticação por header Bearer, sem cookies, então não amplia acesso.
- Compensação parcial se o próprio desfazer falhar (500; a admin vê a cliente sem acesso e repete).
- Sem stack local (sem Docker): a integração real só é testada depois do deploy aprovado (T3, E2E).

## Critérios de aceite

1. Nenhum segredo no repositório; `service_role` só via `Deno.env` dentro da função.
2. 405 fora de POST; 401 sem sessão ou com JWT inválido; 403 para não-admin e admin bloqueado, antes de qualquer escrita.
3. `create_account` vincula ou desfaz; não apaga cliente pré-existente; duplicados → 409.
4. `set_access` recusa a própria conta e contas de admin; bloqueia no banco antes do Auth; falha do ban → 502 com o bloqueio mantido.
5. `reset_access` recusa bloqueadas e admins; `update_email` reverte o Auth em falha.
6. Validação de entrada (UUID, e-mail, `redirect_to` http/https) → 400; mensagens de dependência não vazam.
7. `deno check index.ts` passa; testes do handler passam.
