# O0 — Infraestrutura da orquestração

- **Dono:** Claude · **Revisão:** CXR (`high`) · **Base:** `924c26e` · **Faixa:** commit(s) de O0 em `claude/ciclo-3`

## Objetivo

Permitir que o coordenador (Claude) despache jobs do Codex (`review`/`task`) de
forma segura e recuperável, conforme `docs/orquestracao/ORQUESTRACAO.md` §4.

## Arquivos e travas

- `scripts/orq/codex-job.mjs` — entrada fina (processos, arquivos).
- `scripts/orq/lib/job.ts` — lógica pura: argumentos, lock, memória, prompt, args do codex, thread_id, validação, tentativas, regra de aprovação.
- `scripts/orq/lib/schema.ts` — validador mínimo de JSON Schema (subconjunto usado pelos schemas).
- `scripts/orq/lib/job.test.ts` — vitest.
- `docs/orquestracao/FILA.md`, `docs/orquestracao/tarefas/O0.md`, `.gitignore` (`.orq/`).
- `vitest.config.ts` / `tsconfig.json`: só a inclusão de `scripts/**` (necessária para os testes e o tsc enxergarem `scripts/orq`).
- `docs/PLANO-ATUAL.md`: andamento → FILA; decisão D7.

## Abordagem

`runJob(args, layout, deps)` recebe os efeitos colaterais injetados; a entrada
`.mjs` liga `execFile` (sem shell, `node <codex.js>`), `fs`, `git` e `os.freemem`.
Codex: `codex exec -C <worktree> -s workspace-write -c model_reasoning_effort=<e> --output-schema <abs> -o .orq/runs/<ID>-r<n>.json --json -`
ou `codex exec resume <thread>` (cwd = worktree). Rede só para tarefas `H*`.

## Riscos

- Processo do Codex sobreviver ao timeout no Windows → mata a árvore com `taskkill /T /F`.
- Lock órfão após queda → PID morto = lock obsoleto, removido.
- JSON do Codex de outra tarefa/rodada/commit aceito por engano → validação de `task_id`, `round`, `commit`.

## Critérios de aceite

1. Recusa iniciar se `.orq/locks/codex.lock` tem PID vivo; remove lock de PID morto; sempre libera o próprio lock.
2. Recusa rodada > 3 e `--resume` na rodada 1; recusa memória livre < 1,5 GB.
3. Máximo de 2 tentativas por `<ID>-r<n>`, contadas também entre execuções (`.orq/runs/<ID>-r<n>.attempts`); timeout de 45 min conta como tentativa.
4. Codex chamado com `execFile`, sem shell; worktree de review sujo é recusado e o HEAD é conferido contra o SHA; task exige branch `codex/ciclo-3`.
5. Resultado validado contra o schema (`additionalProperties: false`, enums, required) e contra `task_id`/`round`/`commit`; inválido não é copiado.
6. JSON válido copiado para `docs/orquestracao/revisoes/<ID>-r<n>.json` (task: `.task.json`); `thread_id` do evento `--json` salvo para `--resume`.
7. `isApproved` implementa a regra do coordenador (0 bloqueante, 0 importante, todo critério `verified` com evidência, commit = SHA) e não confia em `verdict`.
8. Nenhum segredo nos arquivos; `.orq/` ignorado pelo Git.

## Rodada 2 (achados de `revisoes/O0-r1.json`)

- **O0-B1 (lock não atômico):** `acquireLock` usa criação exclusiva (`writeFileSync` com flag `wx`) como único passo que concede o lock; lock de PID morto é removido e a criação repetida uma vez (perder a repetição = outro processo venceu). `releaseLock` só remove se o conteúdo ainda for o próprio PID. Testes: 4 processos `node` concorrentes → exatamente 1 `acquired` (o `repro_test` adaptado a processos reais); obsoleto substituído; liberação não apaga lock alheio.
- **O0-I1 (base móvel):** review exige `--base <sha>`; o job resolve com `git rev-parse --verify <base>^{commit}`, recusa base igual ao SHA revisado e base que não seja ancestral (`merge-base --is-ancestor`), e envia o SHA completo no JOB. Task: base = HEAD do worktree resolvido para SHA no despacho.
- **Base desta rodada:** `0113c6c` (O1 já integrada; o diff `0113c6c..<sha>` contém só a correção).
- **Limitação do ambiente do revisor:** o sandbox `workspace-write` do Codex no Windows bloqueia `spawn` (EPERM) e o vitest não carrega a config. A evidência do coordenador está em `.orq/evidence/O0/vitest-r2.log` (60/60 em `scripts/orq` + `scripts/lib`). Não alteramos a sandbox (regra de segurança).

## Rodada 3 (achado `O0-B1-R2` de `revisoes/O0-r2.json`)

- **Tomada de lock obsoleto exclusiva:** só quem cria (mkdir atômico) `<lock>.takeover-<conteúdo morto>` pode remover o lock, e só se ele ainda tiver o mesmo conteúdo; o marcador é removido depois que o lock já não tem esse conteúdo, então um retardatário que o recria vê outro conteúdo e desiste sem apagar nada. Se o processo morrer **dentro** da janela de tomada, o marcador fica e o lock fica ocupado até remoção manual (`.orq/locks/codex.lock.takeover-*`), falha segura.
- **Testes:** intercalação determinística do cenário do revisor (o 2º tomador lê o PID morto, o 1º conclui no meio, o 2º retorna `busy` e o lock continua do 1º) — falhava antes da correção; 6 processos concorrentes recuperando o mesmo lock morto → exatamente 1 `acquired` (5 repetições).
- **Base desta rodada:** `d82d07f`. Evidência: `.orq/evidence/O0/vitest-r3.log` (62/62 + 5× os testes de lock).

## Rodada 4 (achado `O0-B1-R3`; rodada extra autorizada pelo responsável em 2026-10-24)
